## 1. The two game fixes did not both work

`HANDOFF.md` §2 claimed `maze` 0.0 → 65.2% solve rate and `freeway` 0.12 → 3.92
mean return. The 144-run suite (`41650699`) launched after those fixes and all
144 runs completed. Measured on the cluster's own files:

| game | claim | what the suite shows |
|---|---|---|
| `freeway` | 3.92 under random | **0.00**, all 3 seeds, both encoders, 100M steps |
| `maze` | fixed | trains to **4.51**, below its own random baseline of **7.0** |

`freeway` is not broken. On the cluster's file, an UP-only policy scores 8–13 and
a random policy scores exactly 0. Crossing needs ~84 committed UP actions
(336 px at speed 4), so a uniform-sampling policy does a symmetric random walk
with negative drift from the one-lane knockback. Action repeat at 4 and 8 does
not help — it is not a horizon problem.

The sync was fine: the cluster's `freeway.js` matches `origin/main` exactly. Note
that branch `continuous-input` still carries the **pre-fix** freeway (lives = 0,
reset-to-bottom, `score >= 10` WIN cap), because it has not merged `main`.

## 2. PPO solves freeway; IMPALA cannot

New runs against the fixed freeway, 100M steps, `outputs/fwfix_ppo_{nat,icnn}`:

| trainer + encoder | start | max | end |
|---|---|---|---|
| PPO + Nature-CNN (`41768036_1`) | 0.00 | **12.03** | 11.71 |
| PPO + IMPALA-CNN (`41768300_2`) | 0.00 | **12.00** | 11.07 |
| IMPALA, both encoders, 3 seeds | 0.00 | 0.00 | 0.00 |

This reproduces the published result. The IMPALA paper's Atari table
(Espeholt et al. 2018) reports `freeway: ACKTR 0.00, Reactor 31.40,
IMPALA deep multi-task 21.41, IMPALA shallow 0.00, IMPALA deep 0.00`. Entropy-
regularized policy gradients score zero on Freeway; value-based methods with
replay do not. `enduro` shows the identical pattern in that table.

So freeway is a game that **discriminates between trainers**, not a dead row. The
pre-fix version gave PPO a max of 0.18, so the fix is what made it learnable.

`ninja` (0 → 11.27) and `caveflyer` (2.33 → 2.91) also now train above random, so
both below-random rows in `tab:eval` are resolved. 22 of 24 games are healthy.

## 3. Window length changes the headline ratio

Panel A's benchmark times **one 300-step window** after 20 warmup steps
(`bench_vec_rollout.py` has no `--trials`). Episodes truncate at 2000 steps, so
most environments never reset inside the measurement and autoreset cost is
excluded. Two runs on the same node (`holy8a28510`) tested this:

| window | PlayTrain | EnvPool | ratio |
|---|---|---|---|
| 300 steps (`41773579`) | 1.766M | 0.541M | 3.26$\times$ |
| 3000 steps (`41773520`) | 1.705M | 0.623M | **2.74$\times$** |

EnvPool gains **15%** with the longer window while PlayTrain loses 3.5%, so the
ratio drops 16%. **The short window flatters us.** The published 4.03× is a
300-step measurement and is likely optimistic by a similar margin.

This was measured on a different node from the published data, so absolutes are
not comparable — but the 300-vs-3000 contrast is internally valid, both arms in
the same job on the same node. **Re-check on the published node before trusting
the current Table 8 numbers.**

## 5. Normalizer runs in flight

`41774570`, array 1-24, 8 games × 3 seeds, **1B steps**, IMPALA + IMPALA-CNN,
configs in `outputs/_norm/`, manifest `outputs/_norm/manifest.txt`, launcher
`norm.sbatch`. Roughly 1 hour per run, 6 concurrent. At handoff: 1–4 COMPLETED,
5–8 RUNNING, 9–24 PENDING on `QOSMaxGRESPerUser`.

These are the eight games with no analytic score ceiling: `bigfish`, `plunder`,
`starpilot`, `seaquest`, `asteroids`, `space_invaders`, `bossfight`, `pong`.

**Check saturation before using them as `R_max`.** If a curve is still rising at
1B it is a lower bound, not a ceiling, and the appendix source column must say
`best at 1B` rather than `max`.

### Why those eight

Read all 24 game sources. `R_max` is analytic for 15 (score is a bounded counter
over what the level generator places), exact from geometry for `freeway`
(2000 steps ÷ ~84 per crossing ≈ 23), and underivable for these eight — six have
continuous spawners so the ceiling is bounded by time rather than content
(`bigfish` spawns at `rng() < 0.04` per frame, `plunder` at `0.06`, `starpilot`
has a spawner system with per-enemy points, `seaquest` scores
`diverCount * 50` so it is strategy-dependent, `asteroids` splits recursively and
has no WIN state, `space_invaders` regenerates waves), and two are skill-limited
rather than content-limited (`bossfight`, `pong`).

ProcGen's own recipe (Cobbe et al. 2020, §2.2 and Appendix C) is
`R_norm = (R - R_min)/(R_max - R_min)`, with `R_max` trivial for 11 of 16 games,
empirical from the level generator for 3, and "the score PPO achieves after 8
billion timesteps at an 8x larger batch size" for StarPilot and FruitBot. Their
`R_min` is a policy trained with **masked observations**, not a random policy.

### R_min is unresolved

The appendix table currently uses random-policy returns from `tab:eval`. ProcGen
uses a blind policy, which is a stronger floor and matters here: freeway random
is 0 but UP-only is 8–13, so a random floor makes PPO's 12 look like it captured
the whole range when a blind policy would get the same. No `blind`/`mask_obs`
flag exists in either trainer; it needs a config option that zeroes the
observation tensor in the actor path, then 24 short runs.

Also: `R_min` for `maze` and `freeway` in that table is **stale**, predating the
game fixes. Random on the fixed maze scores 7.0.

## 7. Cluster hygiene

The idle-GPU emails come from env-only jobs that request `--gres=gpu:4` while
running `--no-model`. The GPUs were only ever requested to clear the 23-cores-
per-GPU cap on `kempner_h100`.

Requesting **cores without `--gres`** leaves the GPUs schedulable and stops the
emails. `serial_requeue -C genoa` gives AMD Genoa nodes with no GPU and started
in 8 minutes; `holy8a28510` is 192-core Genoa. Note `PreemptMode=REQUEUE` there,
and results are written per game, so a preempted sweep leaves partial
`ab_*_<jobid>.json` files that must be cleared before a rerun.

Queue facts, measured: `sapphire` is ~10h regardless of core count (fairshare,
not capacity — 1 core and 108 cores return the same estimate). `gershman` starts
immediately. `test` starts in minutes, 112 cores, 12h limit.
`intermediate` and `bigmem` refuse this account.

**Panel A's node is AMD Genoa, not Sapphire Rapids.** `holygpu8a17402` is
`amd,genoa`; the per-core panels ran on `holy8a32607`/`32603`, which are
`intel,sapphirerapids`. The figure mixes two CPU vendors across panels and the
appendix does not say so. Sapphire runs ~78% of Genoa's per-thread throughput
here, and the ratio moved too (1.14× → 0.99× at 5 threads), so moving panel A to
sapphire would cost the 4M headline. `bench_vec_scaling_cpu.sbatch` and
`bench_vec_scaling_genoa.sbatch` are committed on the cluster for CPU-partition
runs.

Also: `--export=ALL,WORKERS=1,2,4,...` **silently breaks** — sbatch splits the
value on commas, so only `WORKERS=1` survives. Export the variable in the
submitting shell instead.
