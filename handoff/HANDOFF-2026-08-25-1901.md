## 1. The suite curves had a metric bug, not a game bug

`charts/ep_return_mean` in the DDP learner was a rolling mean over a
**512-entry deque while 6,144 environments were running** (12 workers x 512 envs,
double-buffered 2x256). A 12x undersampled window.

It only matters for a game whose episodes end in sync. `maze` has no failure
state, so every unsolved episode lasts exactly `max_steps` (2,000 frames). All
6,144 environments start together and never drift apart, so ~6,144 truncations
land inside one logging interval and overwrite a 512-slot window several times
over. That produced three artifacts in the maze panel, all from the same cause:

- an opening plateau pinned at exactly 10.00 (only wins had completed),
- a cliff at 12.3M env steps (`6,144 x 2,000`, the first truncation wave),
- a sawtooth of period 11.8M measured by autocorrelation, +0.51, against 12.3M
  predicted. No other game shows periodicity.

Fixed in `playtrain-trainers` `e270ece`, `impala/ddp_learner.py:179`:

    recent_returns: deque = deque(maxlen=8192)   # was 512

**Two earlier diagnoses in this session were wrong** and are recorded here so
they are not retried: it is not the missing failure terminal on its own, and it
is not fixed by shortening the timeout or by re-tuning the level distribution.
Extra EMA smoothing does not help either, because the oscillation is ~28 samples
long at 240 logged points, the same order as the smoothing window.

**PPO has a milder version of the same defect**, `train_ppo_clean.py:1210`:

    recent = completed_returns[-100:]

100 samples over `n_envs = 192`, about 2x undersampled. With 192 environments a
wave cannot flood it the way 6,144 can. Left alone deliberately: `41803949` is
mid-array, and changing the trainer under a running array would leave earlier and
later tasks on different metric definitions. Fix it after that suite drains.

## 2. maze was also made harder, on purpose

Separate from the metric bug. At the old level sizes the task had almost no
dynamic range: random play solved 66%, a trained agent 92%.

`games/js/maze.js`, commit `817082d`:

    mazeDim = Math.floor(rng() * 7) * 2 + 9;    // sizes 9-21, was 5-21

Dropping the two smallest sizes puts random play at **40.7%**, next to real
ProcGen's **44.2%**. Reached through the level distribution rather than by
adopting ProcGen's `timeout = 500`, because the uniform 2,000-frame horizon is a
deliberate PlayTrain config choice.

Measured alternatives, all at the 2,000-frame horizon, random solve rate:

| sizes 5-21, goal random | 65.8% | previous |
| sizes 9-21, goal random | 40.7% | **chosen** |
| sizes 13-21, goal random | 35.3% | harder than ProcGen |
| sizes 5-21, goal far-of-8 | 47.0% | biases goal placement, avoid |
| sizes 9-21, goal far-of-8 | 25.9% | too hard |

A `timeout = 500` change was applied and then **reverted** (`a69ea3c`), because
per-game timeouts break the uniform horizon and the same artifact affects `heist`
and `freeway`, which that change would not have touched.

## 3. Greedy eval disagrees with the training curves

`41853620` finished: six files, `outputs/eval_s3_{icnn,nat}_s{0,1,2}.json`, one
per encoder and seed, 24 games each.

**Do not paste these into `tab:eval` without resolving this first.** Greedy eval
returns far below the training curve on several games:

| game | training curve @100M | greedy eval |
|---|---|---|
| maze | 7.77 | **0.00** |
| ninja | 11.70 | 1.50 |
| caveflyer | ~3.5 | 2.62 |

maze at 0.00 with a random baseline of 3.75 is the striking one. The likely cause
is that `greedy_eval` takes argmax, and a deterministic policy in a maze can loop
forever without reaching the goal, whereas the training return comes from the
stochastic policy. The eval also runs `--max-steps 3000` against training's
2,000. Both need checking before these numbers go in the paper.

Note also that the FIRST eval attempt, `41804054`, is unusable and its output
should be ignored: `tools/eval_final_agents.py` keys its output dict by
`config["game"]`, so feeding it all 144 run dirs collapsed them to 23 rows, each
holding whichever run happened to finish last. Always invoke it with one run per
game.

## 7. Standing hazard

A game file changing mid-array leaves earlier and later tasks disagreeing. This
nearly happened with the PPO suite and maze: variant A landed while `41803949`
was queued but before it had reached its maze tasks, so it picked up the new file
by luck. Check array progress before touching any game file.
