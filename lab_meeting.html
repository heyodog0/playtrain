Browserless game RL

A fast, LLM-generated benchmark for procedural-generalization studies — running JavaScript games at native speed without a browser
Ryan Truong
Lab meeting · April 2026

The puzzle, in one sentence

RL benchmarks force a three-way tradeoff between speed, diversity, and cost of authoring new environments. Today you pick two.

  • Atari: fast, fixed (57 games hand-written 30 years ago), zero authoring
  • ProcGen: fast, 16 procedurally-generated games, requires a custom C++ build
  • Browser/web games: huge corpus, slow (~30 FPS), expensive infra (Playwright + base64)
Core claim: an LLM that writes games against a strict template, executed in a headless Node runtime, gets you all three at once.

ProcGen sets the gold standard

  • Procedural generation: each level a fresh draw from a distribution ⇒ train/test seed splits actually measure generalization, not memorization
  • Fixed action / observation interface across all games (Discrete(15), 64×64 RGB) ⇒ one CNN policy trains on all 16 simultaneously
  • Canonical baseline: PPO + IMPALA-CNN, 25–50M steps, normalized scores (Cobbe et al. 2019)

The benchmark works because the interface is uniform and the levels are infinite. Both properties carry over to anything that respects the same template.

Cobbe, Hesse, Hilton & Schulman 2019 — "Leveraging Procedural Generation to Benchmark RL"

Slow benchmarks compound

A 2× slowdown on env step is not a 2× slowdown on the field — it's a 2× tax on every iteration of every method, every paper, every grad student.

The interesting question isn't whether you can run a benchmark — it's whether iteration cycles are short enough that exploring methods feels free.

Why browser-based RL has been a dead end

  • The DOM is the bottleneck, not JavaScript. A browser RL step is: render → canvas.toDataURL() → base64 encode → IPC to Python → base64 decode → image decode → resize
  • Each round-trip is ~5 ms of overhead before the game does anything useful
  • Playwright + headless Chromium ≈ ~50–200 FPS per env, regardless of how trivial the game is
  • Parallelism is bounded by Chromium memory (~250 MB / instance)

Conclusion: keep the JavaScript, drop the browser.

The gap

Existing benchmarks force a choice between authoring effort and diversity:

  • Hand-written Atari/ProcGen environments: 100s of hours per game
  • Browser-game corpora: cheap to find, expensive to run, never standardized
  • No benchmark exists where game generation itself is cheap, the runtime is fast, and the interface is procedurally-generalizable
Can an LLM produce, against a strict spec, games that pass ProcGen-style validation and run at native JS speed in headless Node?

Architecture (one picture)

Gemini ──generates──▶ games/js/breakout.js (p5.js, Discrete(8), seeded) │ ▼ ┌─────────────────────────────────┐ Python (SB3 PPO) ◀──── │ GameGymEnv (Gymnasium) │ ▲ │ obs │ │ │ │ │ action │ ▼ │ │ ▼ │ binary IPC │ │ reward │ │ │ │ │ ▼ │ │ │ Node worker (game-worker.mjs) │ │ │ │ │ │ │ ▼ │ │ │ p5.js shim on node-canvas │ │ │ (no DOM, no browser) │ │ └─────────────────────────────────┘ │ └──── one Node subprocess per parallel env ────

Every layer is replaceable. The contracts (game template, IPC protocol, Gymnasium API) are the load-bearing pieces.

Method §1 — the game template

One .js file per game, exposing four globals: setup(), draw(), resetGame(seed), getGameState().

Action space

Discrete(8) — abstract directional + button. Identical across every game.

NOOP, LEFT, RIGHT, UP, DOWN,
D, LEFT+D, RIGHT+D

Observation

64×64×3 uint8 — runtime downscales the canvas. Game never touches resolution.

Seeded RNG — same seed + same actions ⇒ bit-identical trajectory.

Mirrors ProcGen's interface deliberately so a single CNN policy can train across the whole catalog.

Method §2 — the LLM generation pipeline

  • Catalogs: 4 JSON files of 25 games each (atari, arcade, nes, mobile, procgen), 100 cataloged total
  • Generator: Gemini 2.5 Flash/Pro receives the catalog entry + GAME_TEMPLATE.md + (optionally) Wikipedia reference
  • Output: a single games/js/{name}.js conforming to the spec
  • Refinement loop: browser game-tester (tools/tester.py) plays the game, captures feedback, re-prompts Gemini with the diff

Generation is cheap (just gen-game atari_games.json breakout, ~30 s) — the costly thing is verifying what came back.

Method §3 — headless Node + p5 shim

Replace the browser with a 200-line shim:

  • node-canvas provides CanvasRenderingContext2D backed by Cairo — no GPU, no compositor
  • p5 shim exposes the p5.js global API (fill, rect, keyIsDown, …) by routing draw calls to the canvas context
  • No requestAnimationFrame: the runtime invokes draw() on demand from the IPC handler, one tick per RL step
  • No event loop coupling: deterministic stepping, no jitter

Net result: a p5.js game runs identically to its browser version, but the entire process is one Node thread.

See poc/p5/ for the shim; notebooks/headless_node_vs_playwright.py for the architecture deep-dive.

Method §4 — the IPC protocol

Python ↔ Node communication. Designed to make the per-step overhead measurable in microseconds.

// header (8 bytes, big-endian)
[ uint32 meta_length ][ uint32 binary_length ]
// then: meta_length bytes of UTF-8 JSON  (cmd, action, seed, ...)
// then: binary_length bytes of raw uint8 obs buffer

# Python decode
obs = np.frombuffer(raw, dtype=np.uint8).reshape(64, 64, 3)
  • No base64, no JSON pixel arrays, no string parsing on the obs
  • Raw uint8 buffer ≈ 12 KB / step — single read() on the pipe
  • Sub-step timing on this path: 0.12 ms for pixel read + transfer (per all_games_benchmark.py)

Method §5 — Gymnasium wrapper

GameGymEnv is a standard gym.Env. Each instance:

  1. Spawns one Node subprocess running game-worker.mjs --game GAME
  2. Holds open stdin/stdout pipes for the lifetime of the env
  3. On reset(seed): writes {cmd: "reset", seed}, reads first frame
  4. On step(action): writes {cmd: "step", action}, reads frame + reward + terminated + truncated + info
  5. On close(): writes {cmd: "close"}, joins subprocess

Parallelism falls out for free via SB3's SubprocVecEnv — N envs ⇒ N Node subprocesses, no shared state, no GIL contention.

Method §6 — the validation suite

Five mechanical checks per game. A game enters the catalog only if it passes all five.

CheckWhat it asserts
API compliancegymnasium.utils.env_checker.check_env passes
DeterminismSeed + 200 random actions ⇒ bit-identical observations, rewards, info["score"] across two runs
Observation sanityShape (64,64,3), dtype uint8, range [0,255], >5 unique values, frame changes within 30 steps
Reward / terminalreward == score_t − score_{t−1} at every step; terminated implies gameState ∈ {WIN, EXIT, GAMEOVER}
ThroughputStep FPS measured, no crashes over 500 steps

This is the contract. An LLM that produces a game passing it is producing a usable RL environment, period.

Method §7 — multi-game vectorized env (ProcGen-style)

Each parallel slot is permanently assigned one game. With 14 games and n_envs_per_game = 4:

vec_env = make_multigame_vec_env(
    games=list_available_games(),       # 14 games
    n_envs_per_game=4,                  # 56 parallel envs total
    seed_range=(0, 200),                # ProcGen train seeds
)
  • On reset, the slot keeps its game and draws a new seed from the train range
  • The PPO rollout buffer collects experience from all 14 games simultaneously
  • One CNN policy must learn to play all of them — generalization across games, not just levels

Method §9 — train / test seed splits

ProcGen convention, applied per game:

SplitSeedsUsed for
Train0 – 199Rollouts during model.learn()
Test (held-out)1000 – 1099EvalCallback + final eval/evaluate.py

Aggregate metric: interquartile mean (IQM) of normalized scores (raw − random) / (best − random), across games. Random baselines collected via just baselines (100 episodes/game, written to outputs/baselines/).

Agarwal et al. 2021 (Deep RL at the Edge of the Statistical Precipice) — IQM is robust to outliers across games.

Validation results — 30 / 30 pass all five checks

  • All 30 games pass API + determinism + obs sanity + reward + throughput
  • Median throughput: ~4,150 FPS (raw env step; range 1.2k–4.8k across games, mean ~3,800)
  • Slowest games are physics-heavy (miner, chaser); paddle / shooter games sit at the top end
  • The 5-check suite is the regression gate — when an LLM-generated game lands, this is what tells you whether it's usable

Re-run any time: just validate. Per-game results in outputs/validation/summary.json.

Implications — RL methods research

  • Iteration cycles drop from days to hours. A 25M-step ProcGen-style sweep finishes in ~5 hours on a laptop. Method ablations become a single afternoon.
  • The benchmark grows with the field. When a new method is sensitive to a property no current game tests, you generate a game that tests it (cost: ~30 s of Gemini + one validation pass).
  • Generalization gets a stronger signal. ProcGen tests generalization across levels of one game; this tests across games, with the same uniform interface.

Implications — LLMs as environment generators

  • "Write a game that passes this validation suite" is itself a benchmark for LLM coding under spec constraints — far more discriminating than "implement quicksort"
  • The validation pass rate per LLM (Gemini Flash vs. Pro vs. Claude Sonnet) is a directly measurable, well-defined number
  • The refinement loop (tester → failure feedback → re-prompt) converts LLM coding into an interactive, gradient-free optimization with a verifiable objective

Open question: does this transfer? An LLM that writes a passing breakout ought to write a passing novel game-genre cousin. We have not yet measured generalization on the LLM side.

Implications — procedural generalization

Two kinds of generalization can now be studied separately on one stack:

AxisOperationalized as
Within-game (ProcGen-style)train seeds 0–199 → test seeds 1000–1099 of the same game
Across-gametrain on subset $G_{\text{train}} \subset \mathcal{G}$ → test on $\mathcal{G} \setminus G_{\text{train}}$

The Discrete(8) / 64×64 RGB interface guarantees the policy network is the same for both — so cross-game transfer is a clean ablation, not an architecture comparison.

Open questions for today

  1. Action space. Is Discrete(8) too narrow for the more complex catalog entries (mario, sonic, vvvvvv), or does the abstraction hold?
  2. Reward shaping. Reward = Δscore. Several games have natural reward shaping the LLM could emit (proximity-to-goal, near-misses) — do we standardize, or accept score-only?
  3. Cross-game splits. 14-game catalog ⇒ only ~3 games to hold out. Is the LLM-generation route the principled way to enlarge $|\mathcal{G}|$, or do we hand-author?
  4. Headline framing. Lead with the runtime (technical novelty) or the generation pipeline (research-enabling) when writing it up?
