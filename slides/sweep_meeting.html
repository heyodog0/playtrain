The ProcGen-style baseline sweep

What we're running on FASRC, why, and exactly how it matches the OpenAI ProcGen paper's methodology
Ryan Truong
Sweep briefing · April 2026

Why run a sweep instead of a single model?

  • Single-seed results are not publishable. Deep RL has ~10% run-to-run variance; one seed could be the peak or the floor of a three-seed distribution. Reviewers will reject.
  • A sweep gives error bars. 3 seeds × 30 games = a distribution of 90 training curves. Any aggregate claim ("our baseline beats random by X") carries bootstrap CIs from this matrix.
  • A sweep is the thing the paper reports. Every ProcGen paper table and figure comes from exactly this kind of grid.
Goal: produce the first sweep-level number for this benchmark — one that's directly comparable to Cobbe et al. (2019) Fig 2–3.

Reward normalization — VecNormalize(ob=False)

ProcGen paper wraps the training env with baselines.VecNormalize(venv, ob=False) — running-mean/std normalization of rewards only, not observations. Same in ours via stable-baselines3.VecNormalize.

PropertyPaperOurs
Normalize observations?NoNo (norm_obs=False)
Normalize rewards (running std)?YesYes (norm_reward=True)
Gamma for reward return0.9990.999
Clip reward10.010.0
Stats saved with model?YesYes → vecnormalize.pkl
Eval env uses same stats?Yes (via dual-role env)Yes (sync_envs_normalization)

Without this, reward magnitudes differ wildly across games (breakout scores in 10s, miner in 100s) and the single cross-game policy's gradient is dominated by whichever game happens to score biggest.

Train/test seed protocol — the generalization contract

ProcGen's defining move: generate 200 training levels, evaluate on 100 unseen ones. The train/test gap is what the benchmark exists to measure.

SplitProcGen paper (easy)Our sweepRole

Test levelsnum_levels=0, start_level=0 (held-out)seeds 1000 – 1099 (per game)EvalCallback every 50k steps
ResamplingFresh seed each episode from the setSame — SeedRangeWrapper draws uniformly
Seeds visible to agent at train time?No seed info in obsNo — seed only controls game reset

The multigame variant additionally logs train-set eval in an eval_train/ directory so Fig 4 (gap) is reproducible.

Cross-game aggregation — IQM over ProcGen's mean

ProcGen paper reports mean normalized return. We report the same plus IQM (interquartile mean) — both available in src/fast_games/metrics.py.

$$\text{normalized}_g = \frac{R_g - R_{\text{random},g}}{R_{\text{best},g} - R_{\text{random},g}}$$

  • Random baseline R_random,g: 100 random-action episodes per game, via just baselines. Committed to outputs/baselines/.
  • Best baseline R_best,g: max over all PPO runs in outputs/experiments/<game>/ppo/ — a stand-in for "expert" until a stronger upper bound exists.
  • IQM: trim top + bottom 25% of normalized scores across (game, seed) pairs, average the middle. Robust to the 1–2 games that might totally fail.

Agarwal, Schwarzer, Castro, Courville & Bellemare 2021 — Deep RL at the Edge of the Statistical Precipice (NeurIPS).

One cell — what a single (game, seed) run executes

Every cell runs exactly the same code path, only the args differ.

uv run fast-games-train \
    --game breakout --seed 0 \
    --config configs/full_run.json \
    --output-dir outputs/sweeps/<sweep_id>/breakout/seed0

Internally: SubprocVecEnv(32) → VecMonitor → VecTransposeImage → VecNormalize → PPO("CnnPolicy", policy_kwargs={ImpalaCNN}) → model.learn(5_000_000, callback=EvalCallback).

Produces (~50 MB per cell):

  • config.json — every hyperparam + git hash + timestamp
  • final_model.zip — policy at 5M steps
  • best_model/ — checkpoint with highest held-out eval return
  • vecnormalize.pkl — reward-normalization running stats
  • eval/evaluations.npz — the file figures.py reads
  • tb/ — TensorBoard logs (for real-time monitoring if wanted)

BLAS pinning is critical: OMP_NUM_THREADS=1, OPENBLAS_NUM_THREADS=1, MKL_NUM_THREADS=1. Without it, 32 envs × 32 BLAS threads = 1024 threads fighting for 32 cores, and training slows 5–10×.

Why CPU, not GPU, for this workload

Our env is a Node.js subprocess per slot — CPU-bound by design. On a GPU, the env becomes the bottleneck, not the CNN.

SetupFPSCNN utilEnv utilCost / run
FASRC sapphire (32 cores)~750high (single-thread PyTorch)highcheap
FASRC 1× V100~3,000low (GPU idle waiting)maxed~3× CPU
FASRC 1× A100~4,500very lowmaxed~10× CPU

Every extra dollar of GPU gets a smaller speedup because the CPU-side env dominates. CPU's the right call unless we port games to a vectorized GPU-native runtime (not on this paper's scope).

Concerns & what could still be wrong

  • 5M may be too few steps to see the paper's mean-normalized-return curves asymptote. Pilot will tell us; 25M is the Plan B.
  • 32 envs instead of 64 doubles the wall-clock per effective step vs. paper. Numbers will be directionally right but biased toward noisier gradients.
  • "Best baseline" is a moving target. constants.py uses the max over historical PPO runs as the denominator — so as training improves, normalization tightens. Fine for within-paper comparisons, bad for cross-paper comparisons until we freeze a snapshot.
  • Action-space mismatch: ProcGen is Discrete(15), ours Discrete(8). The policy head size differs; the qualitative behavior should be identical but absolute numbers aren't directly comparable.
  • No difficulty modes on our games yet. Can't run an "easy vs hard" axis like the paper does in Fig 6.
None of these are blockers for the first sweep — they're the list of things to fix after we see what 5M-step numbers look like.

What comes after this sweep

  1. 25M-step rerun for paper numbers. Same infrastructure, bumped total_timesteps, ~9 h / cell; fits in the same 12 h walltime.
  2. Cross-game generalization sweep: train on 24 games, test on 6 held-out ones. Same runtime, different game-split manifest.
  3. LLM-as-generator benchmark: freeze a catalog, measure validation pass rate × refinement rounds for Gemini Flash / Pro / Claude Sonnet. No RL sweep needed; just generation + validation.
  4. Ablations: IMPALA-CNN off (NatureCNN), VecNormalize off, Discrete(8) alternatives. Each = one smaller sweep.
  5. Paper writeup: runtime + catalog + this baseline sweep + cross-game figure.
